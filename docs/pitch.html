The thesis

Find out what you need.
Find out who you are. Then serve you.

Three things annoy me about most support bots. They ask me to log in before they know what I want. They make me repeat things I already said. And when they cannot help, they keep trying instead of getting me a person. Bookly works in three steps, in that order, on purpose.

1 · What you need

A policy question is answered straight away. No login, because the answer does not depend on who is asking.

modelProposes the intent.

codeOwns the confidence floor and the routing table.

2 · Who you are

Email and ZIP once. Give all of it in one sentence and you are not asked for any of it again.

modelCollects the two factors.

codeCompares them and mints a scoped token.

3 · Serve you

Two open orders? It asks which one. Outside the return window? A clear no, with the arithmetic. It does not stall.

modelPicks the tool and writes the reply.

codeDecides which tools exist at all.

The same order is what makes it safe to ship. A system prompt asking the model not to do something is not enough.

Orchestration

No framework: The loop is the architecture

The tool-calling loop is Python, not LangChain and not the SDK’s runner. It recomputes the tool list on every iteration, so verifying mid-turn widens tool-access for the very next model call.

Memory

Great CX through slots, not stages

Bookly uses turn history, session state and Postgres. Someone who gives email, ZIP and order number in one sentence is never walked back through three questions.

Prompts

The prompt asks while the code enforces

Bookly never asserts a fact a tool did not return and never guesses an email. The return windows and the tool gating are not in the prompt. If the model ignored every word of it, you would get a clumsier reply, not a policy breach.

Guardrails

One set per step — and not one of them is a sentence in a prompt

Guardrails don't add any notable CX friction. They are what lets us promise the things on the first slide and still lets Bookly pass a security audit.

Step 1 · What you need
  • Routing is its own constrained call, not a side effect of generation.
  • Confidence under 0.6 asks a clarifying question instead of guessing.
  • While the intent is unclear, no customer-data tool is sent at all.
  • If the router fails, it falls back to keywords — never to “unclear”, which would silently disarm the agent.
Step 2 · Who you are
  • The model never compares the ZIP. It receives a boolean.
  • A wrong ZIP and an unknown email fail identically — no account-enumeration.
  • Lock after three failed attempts. And verify_customer disappears from the tool list.
  • The token never enters the transcript, so it cannot be echoed back out.
Step 3 · Serve you
  • Tools are filtered by state before the model sees them.
  • Return windows are a pure function; the write path re-validates rather than trusting the model.
  • No fact may be stated that a tool did not return.
  • Loop budget spent, or a tool says human-review — hand off, with the working attached.

Every one of these is a line of Python that runs whether or not the model co-operates. Enforceable guardrails protecting Bookly against bad actors.

The headline guardrail

The token service: a key card cut for one customer

Show ID at the desk and you get a key card. It opens your room — not the one next door, not the manager’s office — and it stops working when you check out. That card is what step 2 issues, and every action in step 3 has to use it. The sub claim is the room number — customer 1 is Sarah.

{ "iss": "bookly-identity",
  "sub": "1",          <- customers.id = Sarah
  "scope": ["orders:read",
            "returns:write",
            "notifications:send"],
  "amr":  ["email", "shipping_zip"],
  "exp":  iat + 600 }  <- about one conversation

And no tool accepts a customer id. It is not a parameter in any schema the model receives. Every scoped read derives it from sub, server-side. There is no argument through which to ask for someone else.

-- Sarah asks for Marcus’s order
SELECT order_number, carrier, tracking_no
  FROM orders
 WHERE customer_id = 1   <- the same 1
   AND upper(order_number) = upper('BK-10102')
0 rows · 2.5 ms

The polite refusal is the model behaving well. The empty result is the part that still holds when it doesn’t.

The trade-off, and the production answer: minting is hand-rolled, which is not what you would ship. In production this is a token exchange against the IdP you already run — client credentials for the service leg, RFC 8693 for the user leg. The plumbing changes; the property that matters does not.

Moving to production

An even greater CX, and the scale to serve it

Greater CX
  • Stream the responses. The biggest remaining latency win. The agent speaks, calls a tool, speaks again — and today the customer waits through all of it before seeing a word.
  • Grow the eval set from production traffic. My test set is made up. At go-live I would collect real requests and evaluate against those.
  • Give the policy engine to the CX team. Changing a return window from 30 to 60 days should not need a deploy.
Scalability
  • Persist sessions to Redis. Sessions are a dict in memory today. Fine for a prototype, not under load.
  • Run the evals against the live model in CI. They run on the scripted engine, so they prove the orchestration and say nothing about how the model behaves under it.
  • Upgrade the token service. Hand-rolled minting becomes a token exchange against the IdP you already run — same scoped card, issued by a system you already trust. Appendix A.

The three steps do not change in production. What changes is how fast they feel, how much load they take, and who owns the rules. If I could only do one first: run it against real traffic. Customers will confirm my annoyances or hand me better ones.

Appendix · if asked

The token service, and what would replace it

Today · hand-rolled
  • hmac.compare_digest against my own table.
  • HS256 — one shared secret both signs and verifies, so anything that can check a token can also mint one.
  • amr is self-attested: my word, in a token I signed, for how I checked.
  • No revocation. A JWT is valid until exp — the 10-minute TTL is damage limitation, not a kill switch.
  • No key rotation, no kid. Rotating invalidates every live token at once.
  • Factors are knowledge-based: email plus a ZIP.
Production · the IdP you already run
  • Client authentication by private_key_jwt or mTLS — or workload identity, and no static credential at all.
  • RFC 8693 token exchange mints a token scoped to one customer, audienced to the order service.
  • An act claim records the delegation — the agent, acting for Sarah — revocable without touching her account.
  • Asymmetric signing plus JWKS: verifiers can verify and can never mint.
  • The IdP owns MFA, lockout, risk signals, revocation and the audit trail.
  • Factors become possession-based: a link, a code, a passkey.

The seam is 104 lines and two functions — twelve call sites, all through that pair. The swap makes identity.py smaller, and none of this moves: no tool accepts a customer id, every read still derives from sub, tools stay gated on auth state.
